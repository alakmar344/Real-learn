14The API Surface — Every Endpoint

Twelve routes, one file. This chapter is the complete reference: method, path, authentication, rate budget, purpose, and response shape for everything registered in server.js.

Conventions

Every route in server.js is assembled from the same three building blocks: a rate limiter (the shared apiRateLimiter at 20 requests per 60 seconds unless the route carries its own), the requireAuth middleware from lib/auth.js for everything that reads or writes user data, and a handler that returns JSON — except for the two payload outliers, /api/tts (binary audio/mpeg) and /api/generate-lesson (a text/event-stream SSE response). Rate-limited rejections are uniform: HTTP 429 with a Retry-After header and the body {"error": "Too many requests. Please slow down."}. Only two routes are unauthenticated by design: /health (for uptime monitors) and /api/feedback (whose privacy promise is that feedback is never linkable to a person, so demanding a token would defeat the point).

Health and diagnostics

GET /health is unauthenticated but carries its own 120/min limiter, because every hit pings MongoDB — without a budget it would be a free amplification vector onto the database. The response combines a Mongo ping with getProviderHealthSnapshot() from the AI engine: if any provider circuit is open or has consecutive failures, dependencies.ai reports "degraded". The status code follows Mongo only (503 when it is down), and the response is cacheable for 10 seconds. GET /api/auth-debug is the deliberate oddity: an authenticated token-verification oracle that reports exactly why a Clerk token passes or fails (inspectToken plus verifyClerkToken). Because an oracle like this aids attackers probing tokens, it returns 404 unless AUTH_DEBUG_ENABLED=true or the host is explicitly in development — a gate the source comments note was tightened after NODE_ENV !== "production" left it wide open on hosts that forgot to set the variable.

The consent and privacy family

Five endpoints implement the legal-compliance surface, all writing to the agreements collection keyed on {clerkId, type}. The two writers, POST /api/agreement (type cookie-consent) and POST /api/legal-consent (type legal-consent), share a hardening pattern: the clerkId always comes from the verified token, never the body (an IDOR fix); client-supplied timestamps are parse-validated; the stored deviceIp is anonymized to a network prefix by anonymizeIp (last IPv4 octet zeroed, IPv6 collapsed to its first three groups); and the User-Agent is stored only as a salted SHA-256 hash via hashUserAgent. Because Clerk JWTs carry no email claim, a body-supplied email is accepted only after sanitizeClientEmail validation (RFC 3696's 320-char maximum, real address shape) and is flagged with emailSource: "client-unverified" so downstream consumers never treat it as verified.

The two status readers return the stored record with short private cache headers (max-age=300 on a hit, max-age=60 on a miss) so the client can re-prompt when a policy version bumps. GET /api/export-data rounds out the data-subject rights: it matches strictly on the verified clerkId — matching on email as well could leak records created by another account with a spoofed address — and sanitizes the download filename (reallearn-data-<id>.json) to header-safe characters to prevent Content-Disposition injection.

Deletion is a two-phase operation

DELETE /api/account deletes MongoDB data and the Clerk account in sequence, and its error responses encode partial success honestly: if Mongo deletion succeeds but the Clerk Backend API call fails, the client receives a 502 with "Your stored data was removed, but the account could not be deleted." Anonymous feedback records are intentionally left untouched — they carry no clerkId, so there is nothing to link and nothing to delete.

TTS: the binary outlier

POST /api/tts synthesizes speech through node-edge-tts and is engineered around the fact that audio is the largest payload the server emits (~6 KB per second of speech). Input is tightly locked: text capped at 2,000 characters, lang restricted to the 13-entry SPEECH_LANG_TO_VOICE map (an arbitrary string would be an SSML injection channel via xml:lang), and rate/pitch/volume matched against strict prosody regexes such as /^[+-]?\d{1,3}(\.\d{1,2})?%$/. A SHA-256 content hash over text, voice, and prosody keys both a 16 MB in-memory LRU (24-hour TTL) and an ETag, so replays are served from memory and browsers revalidate to a 304 instead of re-downloading. Cache misses pass a concurrency gate of MAX_CONCURRENT_TTS_SYNTHESES = 8; beyond that the endpoint degrades to a fast 503 with Retry-After: 2 rather than exhausting sockets and disk. Temp files carry a random UUID suffix so concurrent requests for the same text never race on the same path.

Anatomy of the SSE stream

POST /api/generate-lesson deserves its own dissection because it is the only long-lived response. After validation, moderation prefiltering, and a cache check, the handler flushes SSE headers (Content-Type: text/event-stream; charset=utf-8, Cache-Control: no-cache, no-transform, X-Accel-Buffering: no) and starts a heartbeat: a ping event every HEARTBEAT_INTERVAL_MS (default 15,000 ms, clamped to at most 55,000 ms) keeps proxies from timing out the idle connection. Progress is a staged percentage that the frontend renders as the loading cinematic:

A cache hit takes a short-circuit path that writes lesson and done immediately — wrapped in its own try/catch, because a client that aborts mid-write would otherwise turn res.write into an unhandled rejection that kills the whole Node process. The main path registers req.on("aborted"), res.on("close"), and res.on("error") handlers before flushing headers, all funneling into a single idempotent finishRequest() that aborts generation, clears the heartbeat and every progress ticker, and releases both the global and per-user concurrency slots. Every write goes through safeWrite, which checks res.writableEnded and swallows socket errors.

res.write(`event: lesson\ndata: ${JSON.stringify(cachedLesson)}\n\n`);
res.write(`event: done\ndata: ${JSON.stringify({ ok: true })}\n\n`);

The terminal error handler

The last middleware registered is a four-arg Express error handler, and its existence is itself a security control: without it, Express's default finalhandler echoes err.stack to the client whenever NODE_ENV is not "production". It maps malformed JSON bodies to 400 ("Invalid JSON in request body"), over-limit payloads to 413, CORS denials to 403 ("Origin not allowed"), and everything else to a bare 500 "Internal server error" — with full detail logged server-side only. If headers were already sent (an SSE stream mid-flight), it simply ends the response, since nothing further is safe to write.
