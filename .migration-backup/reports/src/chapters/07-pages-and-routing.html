Part II · The Frontend

07Pages & Routing

Ten routes cover the entire product: a homepage that asks one question, a learn page that is really a five-state machine, a progress dashboard, a 928-line settings page, four legal surfaces, and two Clerk auth pages — all guarded by a single middleware.

The route map

The App Router tree under frontend/app/ contains exactly ten page.tsx files. Alongside them sit layout.tsx (the root layout described in Chapter 06), not-found.tsx (a custom 404 with a display-face "404" numeral and a single accent-colored link home), and two metadata routes: robots.ts, which allows all crawlers except on /api/ and /_next/, and sitemap.ts, which lists seven URLs with priorities descending from the homepage (1.0) through /learn (0.9) to the auth pages (0.5).

Protection is enforced centrally in middleware.ts: a createRouteMatcher allowlist marks /, the auth routes, /api/webhooks(.*), and /legal(.*) as public; everything else redirects anonymous users to /sign-in?redirect_url=…. A second matcher sends already-signed-in users away from the auth pages. The settings page adds its own belt-and-suspenders effect that pushes to /sign-in?redirect_url=/settings once Clerk reports isLoaded && !isSignedIn — deliberately inside a useEffect, with a comment noting that calling router.push during render is illegal in React.

The homepage: one input, three moments

app/page.tsx is intentionally small. Its visible hero is a time-of-day greeting from greetingForHour() — "Still up?" before 4 a.m., "Morning", "Hey", "Evening", "Late night mode" after 9 p.m. — joined to the signed-in user's Clerk firstName. Below it sit QuestionInput (the primary action) and HomeStats (the daily spark topic, a resume card, and a light progress link). The footer and the FeedbackGate review prompt are loaded with next/dynamic; while a lesson generates, a full-screen LoadingCinematic overlays the page, keyed to the loadingQuestion state.

The page also carries one invisible responsibility: a one-time sync of locally recorded legal consent to the backend. If a visitor accepted the pre-sign-in consent while anonymous and then signs in, an effect reads the local record via readLegalConsent(), checks it is current (isConsentCurrent), POSTs it to /api/legal-consent with the Clerk token and email, and stamps the local record with syncedClerkId so the sync never repeats.

The learn page: a five-state machine

app/learn/page.tsx is the largest interactive page and renders one of five mutually exclusive states, evaluated in order. First, a hydration gate: because lessonStore is persisted, rendering stored state on the first client render would mismatch the SSR HTML, so until useMounted() flips true the page shows a skeleton scaffold (a title bar, a rail line, and three SkeletonCard placeholders). Second, an error state rendered by ErrorState, whose Try Again button re-invokes generateLesson(question, false). Third, the loading state: LoadingCinematic stays up while isLoading or during a 420 ms isRevealing fade guarded by a revealedLessonRef — the file's comment documents a real bug where including isRevealing in the effect's dependency array cleared its own timer and left an invisible overlay blocking a blank page forever. Fourth, an empty state ("No lesson loaded yet") with a single Go Home action. Fifth, the lesson itself.

The lesson view composes a sticky glass header (a FAST or GUIDED pill plus the question as the page's h1, per a WCAG note in the code), the ProgressRail, one PartCard per part, and — once showCompletion flips — the lazy-loaded CompletionScreen and FollowUpBox. All quiz passes funnel through a single handlePartPass(part, score) function that fires haptics and confetti, advances the store via passPart, and records engagement with idempotency keys:

const lessonSignature =
  `${lesson.question ?? lesson.topic ?? ""}|${language}|${lesson.lessonId ?? ""}`;
recordPartPassed({
  score, maxPerPart, language, subject: part.subject,
  creditKey: `part|${lessonSignature}|${part.partNumber}`,
});

The credit key folds in the per-instance lessonId, so retaking a quiz on the same lesson never re-awards XP, but generating a fresh lesson for the same question tomorrow earns credit again. The same function detects the final part, sums first-attempt scores, and calls recordLessonCompleted. Two guards show how defensively this page is written: a part that arrives with an empty quiz bypasses the sheet entirely (opening a zero-question quiz would deadlock the journey), and a persistence effect upserts the whole journey into savedJourneysStore on every progress change, keyed by journeySignature(question, firstPartTitle) plus the first eight characters of lessonId.

Progress and settings: the two dashboards

app/progress/page.tsx reads seventeen fields from progressStore through a single useShallow selector and renders stat tiles, a DailyGoalRing, a dynamically imported ActivityHeatmap and AchievementsGrid (each with skeleton fallbacks), and level information from levelInfo(xp). It contains one subtle correctness decision: the stored streak only changes when a part is passed, so a lapsed streak would display as alive forever. The page computes displayStreak from daysBetween(dayKey(), lastActiveDay) and shows zero once the gap exceeds one day — unless the gap is exactly two and a streak freeze remains, in which case the streak is still savable and still shown.

app/settings/page.tsx is the frontend's largest file because it is where every preference and privacy control converges: theme selection from THEME_OPTIONS, language and level selectors, the Fast/Explain mode choice, the Auto/Lite/Rich performance mode from PERF_MODE_OPTIONS, and the learning-personalization checklist and notes (sanitized through sanitizeChecklist/sanitizeNotes, capped at 500 characters). Its cookie-consent row treats the server-side record as the source of truth for signed-in users — fetchCookieConsentStatus(getToken) first, localStorage fallback — and refreshes on the consent events plus a window-focus listener that only refires after 30 seconds hidden, a guard the changelog describes as focus-DoS protection. The Delete My Data flow is the most involved: a ConfirmModal, a DELETE to /api/account, cancelPendingDebouncedWrites() so a queued store write cannot resurrect deleted data, dynamic matching of reallearn-* localStorage keys, clearArchivedLessons() against IndexedDB, and finally an awaited Clerk signOut(). An adjacent Export My Data handler downloads the user's local record.

Legal and auth surfaces

The legal section is the only place the frontend uses a server component with search params. app/legal/page.tsx awaits searchParams, reads tab (defaulting to privacy), and renders one of the three policy components inside a <nav aria-label="Legal documents"> whose links carry aria-current="page" on the active tab — the three policies are imported directly from their sibling routes, so /legal?tab=terms and /legal/terms render identical content. The policies themselves are long static documents (the privacy policy alone is 699 lines) whose version constants live in lib/legalConsent.ts: privacy 2.7, terms 2.5, cookies 2.3. Bumping any of them re-triggers the consent prompt for every user.

The auth pages are thin wrappers around Clerk's <SignIn> and <SignUp> components using optional catch-all segments ([[...sign-in]]). Their only custom code is an appearance object that maps Clerk's elements onto the design system — var(--bg-card) for the card, var(--accent) with an --accent-hover hover for the primary button, var(--font-display) for the title — so the third-party auth UI wears the house style. AppShell hides the sidebar chrome on these routes via a HIDE_SIDEBAR_PREFIXES check while still rendering the #main-content anchor, so the skip-to-content link works on every page.

The hydration-gate pattern

Three pages — learn, progress, and settings — open with the same two lines: const mounted = useMounted(), then a skeleton return until it flips. The reason is structural: all three render from persisted Zustand stores, and the server has no localStorage, so the SSR HTML always shows defaults. Rendering persisted values on the first client render would make React's hydration diff fail. The gate trades one skeleton frame for deterministic hydration, and the skeleton components (Skeleton, SkeletonCard, SkeletonTile) are shaped like the real layout so the swap does not shift content.

Navigation affordances beyond the router

Routing in RealLearn is not only URL changes. The sidebar's saved-lessons list re-enters /learn by loading an archived lesson into lessonStore and then pushing the route — no network involved. HomeStats does the same for its resume card, and routes signed-out visitors to /sign-in with an encoded redirect_url rather than letting an unauthenticated lesson request bounce off the protected route with an error flash. Finally, next.config.js maintains three permanent redirects that fold /reallan, /reallan/:path*, and /real-learn into the canonical tree — the routing layer absorbing a brand misspelling so deep links never 404.
