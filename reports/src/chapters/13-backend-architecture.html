Part III · The Backend

13Backend Architecture

A single Express process on Render carries the entire server side of RealLearn: twelve endpoints, twelve library modules, a two-tier cache, and a defense-in-depth middleware stack — all in plain JavaScript ES modules.

One process, one entrypoint

The backend is a Node.js application (reallearn-backend, version 1.2.0, "type": "module") whose entire routing surface lives in a single 2,262-line entrypoint, backend/src/server.js. There is no framework beyond Express 4 (express@^4.21.2), no ORM, and no build step: npm start runs node src/server.js, and npm run dev adds --watch. The process listens on process.env.PORT with a default of 10000 — Render's convention — and sets app.set("trust proxy", 1) so req.ip reflects the real client behind Render's proxy rather than the proxy itself, which matters for both rate limiting and the anonymized IP prefixes written into consent records.

The middleware pipeline

Requests pass through a fixed pipeline before touching any route handler. First CORS: allowed origins come from FRONTEND_ORIGIN (comma-separated) with a fallback of https://reallearn.site and https://real-learn.onrender.com; denied origins get logged and rejected with a 403 by the terminal error handler. Second, body parsing with a hard cap — express.json({ limit: "100kb" }) — because every legitimate body here is a question plus a few enum fields. Third, compression: compression@1.8 negotiates Brotli first at quality 5 (set explicitly through zlib.constants.BROTLI_PARAM_QUALITY), falls back to gzip level 6, and compresses anything at or above a 128-byte threshold. The one exemption is the SSE route: the filter returns false for /api/generate-lesson, because buffering an event stream would delay heartbeats.

A dedicated securityHeaders middleware then applies X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, a locked-down Permissions-Policy, and — unless NODE_ENV === "development" — HSTS with max-age=63072000; includeSubDomains; preload and a Content-Security-Policy of default-src 'none'; base-uri 'self'; form-action 'self'. The gate is deliberately inverted: hardening applies unless the host is explicitly in development, so a forgotten NODE_ENV fails safe rather than silently dropping HSTS.

Fail-safe by default

Two recurring patterns define this codebase's security posture. Gates fail closed (security headers apply unless explicitly in development; unknown token shapes never earn a rate-limit bucket), and every background task is non-fatal (index creation, IP scrubbing, and cache writes log errors and retry on the next boot instead of crashing the process).

Rate limiting as a two-gate chain

The factory createRateLimiter({ windowMs, max, ipMultiplier = 5 }) returns not one limiter but an array of two express-rate-limit instances that Express flattens into the middleware chain. Gate one is an always-on IP backstop capped at max * ipMultiplier, counting every request from an IP regardless of token. Gate two is the per-caller bucket: keyed on a SHA-256 hash of the bearer token when one is present, or on the IP otherwise. The design closes a real hole documented in the source — the token is unverified at this layer, so three safeguards apply: only JWT-shaped tokens (matching JWT_SHAPE_PATTERN, three base64url segments of bounded length) count as tokens at all; each IP may mint at most MAX_TOKEN_KEYS_PER_IP = 200 distinct token buckets per window before isTokenSpray collapses it into one shared spray: bucket; and IPv6 callers are keyed on their /64 prefix via rateLimitIpKey, since a residential IPv6 allocation would otherwise hand an attacker 264 fresh buckets.

The general API limiter defaults to 20 requests per 60 seconds (DEFAULT_RATE_LIMIT_MAX_REQUESTS = 20, DEFAULT_RATE_LIMIT_WINDOW_MS = 60000, both overridable by env). Three routes get their own budgets: /health at 120/min, /api/feedback at 5/min with ipMultiplier: 2, and /api/tts at 30/min. On top of rate limits, lesson generation has concurrency gates: at most MAX_CONCURRENT_LESSON_REQUESTS = 6 in flight globally and MAX_CONCURRENT_LESSON_REQUESTS_PER_USER = 2 per verified user, so one user cannot occupy every slot with 20–60-second explain-mode generations.

Authentication: Clerk JWTs verified with jose

Every data endpoint except /health and /api/feedback passes through requireAuth from lib/auth.js. Verification is done locally with jose: the primary path fetches the issuer's JWKS from <issuer>/.well-known/jwks.json (cached in an LRU capped at 32 entries with a one-hour TTL, because the issuer string comes from the token's unverified iss claim and an unbounded map would be a memory-growth vector), and a PEM public key imported via importSPKI serves as an offline fallback when the JWKS endpoint is unreachable. Issuer trust is an explicit allowlist: the configured CLERK_FRONTEND_API (default https://clerk.reallearn.site), any CLERK_ADDITIONAL_ISSUERS entries, and *.reallearn.site over HTTPS. Shared Clerk dev domains (*.clerk.accounts.dev) are trusted only behind the explicit CLERK_ALLOW_DEV_ISSUERS=true flag — the source notes that anyone can mint valid tokens on those multi-tenant domains, so trusting them by NODE_ENV alone would be an authentication bypass one misconfigured host away. In production, the token's azp (authorized party) claim is additionally pinned to the known frontend origins.

Caching tiers

The backend runs four distinct caches, each sized to its payload. The lesson cache (lessonCache.js) is the important one: tier 1 is an in-memory LRU of 100 entries; tier 2 is the MongoDB lessonCache collection with a TTL index, shared across instances and restarts. Keys are SHA-256 hashes over the normalized question (trimmed, lowercased, whitespace-collapsed) plus language, level, mode, and personalization, so trivially different phrasings of the same question still hit. The TTL is deliberately modest — six hours — because Part 3 of every lesson is grounded in current news. A cache hit turns a 20–60-second pipeline into a single lookup and legitimately skips Serper, Gemma, and both moderation passes, since the cached lesson passed all of them when first generated. The other caches: a 16 MB byte-budgeted LRU for synthesized TTS audio (24-hour TTL, ETag revalidation), a 200-entry, 10-minute LRU for Serper contexts, and the JWKS LRU in auth.js.

Startup, shutdown, and operational posture

validateStartupConfig() refuses to boot unless at least one AI provider is configured (CEREBRAS_API_KEY, or CLOUDFLARE_API_TOKEN plus CLOUDFLARE_ACCOUNT_ID). After app.listen, three fire-and-forget background jobs run: startPeriodicWarmUp() keeps the Cloudflare fallback model warm (only if Cloudflare is configured), scrubStoredConsentIps() retroactively anonymizes any raw IPs left by earlier releases, and ensureUserDataIndexes() creates the MongoDB indexes that keep consent lookups, exports, and deletions from becoming collection scans.

server.headersTimeout = 15_000;
server.requestTimeout = 30_000;
// Keep idle keep-alive sockets on a short leash as well.
server.keepAliveTimeout = 10_000;

Those three timeouts are Slowloris hardening: Node's defaults (60s/300s) would let a client hold sockets hostage far longer than uploading a sub-100 kb body requires, and they apply only to request reception, so long-lived SSE responses are unaffected. Shutdown is graceful: on SIGTERM or SIGINT the server stops accepting connections, drains in-flight requests, and force-exits after a 30-second deadline. Configuration is env-driven throughout — 63 environment variables are referenced across the repository, most with clamped, validated defaults (for example LESSON_TIMEOUT_MS is clamped between 30,000 and 600,000 ms, with a warning logged when a configured value is adjusted).

What the tests cover

The suite runs on Node's built-in runner (npm test → node --test): 28 tests across four files — gemma-engine.test.js (13), personalization.test.js (8), moderation.test.js (5), and search-index.test.js (2). The weighting mirrors the risk: the AI engine's retry, circuit-breaker, and racing logic gets the deepest coverage, followed by the personalization sanitizer and the moderation regression suite that guards against false positives on legitimate educational questions.
